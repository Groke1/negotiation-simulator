# ТЗ — фронтенд, модуль «Конструктор» (Author Console)

> Дополняет frontend_training_tz.md и arena_frontend_tz.md по формату, но это отдельное приложение — доступно только роли `methodist` (server_app_tz.md, раздел 1), не общий клиент с «Обучением». Опирается на эндпоинты `/api/scenarios*` из backend_tz.md и server_app_tz.md. Данных для «Обучения»/«Арены» (сессии, профиль) Конструктор не читает и не показывает — это зона куратор-дашборда, отдельное ТЗ.

---

## 0. Принцип

Конструктор — рабочий инструмент методиста, не отдельный «творческий редактор с нуля»: основной путь — **AI предлагает черновик → методист проверяет и правит → публикует**, ручное создание с нуля возможно, но не основной сценарий использования (документ 4, раздел 5.1–5.2: «AI-создание — основной режим MVP»).

Ключевое разграничение ответственности между экранами и сервером: клиент **не имеет собственной логики валидации графа** (обход на тупики/циклы/недостижимые ветки) — это всегда серверный вызов `POST /scenarios/{id}/validate` (server_app_tz.md, раздел 3.1). Клиент может делать только поверхностную проверку формы (обязательные поля заполнены) до отправки — не дублировать логику структурной проверки на фронте.

## 1. Библиотека тренировок

**Назначение.** Точка входа — список всех Scenario методиста (и, опционально, общих в организации).

**Содержимое:**
- Таблица: название, статус (Черновик/Опубликовано), версия, дата изменения.
- Кнопка «Создать тренировку» → экран 2.
- Фильтр по статусу.

**Данные с сервера:** `GET /api/scenarios`.

**Переходы:** клик по строке → экран 3 (открыть существующий черновик или опубликованный сценарий на редактирование — редактирование опубликованного создаёт новую версию, не правит текущую вживую, см. экран 8).

---

## 2. Создание (текстом)

**Назначение.** Основной вход в создание — естественноязычное описание задачи, не форма с десятками полей.

**Содержимое:**
- Большое текстовое поле «Опишите тренировку своими словами» с примером-плейсхолдером (пример из документа 4: «Создай тренировку для менеджера по продажам. Клиент хочет продлить контракт...»).
- Кнопка «Создать с помощью AI».
- Индикатор оставшихся генераций на сегодня (`ai_generations`, лимит из server_app_tz.md, нефункциональные требования) — например «Осталось генераций сегодня: 7» — чтобы методист видел ограничение до, а не после отказа сервера.
- Ссылка «Создать вручную» — альтернативный путь, ведёт сразу на экран 3 с пустой структурой (для MVP — упрощённая форма, документ 4, раздел 5.2).

**Данные и действие:** `POST /api/scenarios/generate` с текстом задачи → ответ содержит `scenario_draft` и `ai_generation_id`.

**Переход:** → экран 3, с уже заполненной структурой из `scenario_draft`.

---

## 3. Черновик — редактор структуры

**Назначение.** Основной экран правки Scenario как объекта (не графа — граф отдельно, экран 4).

**Содержимое (поля Scenario, architecture_v3.md раздел 6):**
- Название, описание контекста.
- Роли (learner/partner — названия).
- Цели, интересы, ограничения — каждое как список коротких пунктов на сторону.
- Параметры сделки (`parameters`) — ключ/начальное значение/единица.
- Скрытая информация (`private_information`) — по сторонам.
- Сложность (`difficulty`: L1/L2/L3).
- Каналы (`channels`): переключатели Chat / Voice (Meeting — не в MVP, переключатель скрыт или задизейблен с пометкой «скоро»).
- Поддерживаемые режимы (`mode_support`): переключатели «Обычная тренировка» / «Арена».

**Данные и действие:** `PUT /api/scenarios/{id}` при сохранении изменений (автосохранение или явная кнопка «Сохранить» — на усмотрение реализации, но не блокировать переход на следующий экран до сохранения).

**Переход:** → экран 4.

---

## 4. Переговорное дерево

**Назначение.** Визуальный редактор графа узлов — самый технически сложный экран, основа для React Flow (implementation_roadmap.md, стек).

**Содержимое:**
- Холст с узлами (открытие/эскалация/развязка — три визуально различаемых типа блока, architecture_v2/v3).
- Узел: реплика партнёра (`text`), эмоция (`emotion`), список действий обучающегося с их `label`, `semantic_action`, привязанными `indicator_tags`.
- Добавление действия — выбор `semantic_action` из фиксированного словаря (`ASK_QUESTION`, `MAKE_PROPOSAL`, `MAKE_CONCESSION`, `REQUEST_RECIPROCITY`, `HOLD_BOUNDARY`, `CHANGE_TOPIC`, `PAUSE`, `SUMMARIZE`, `CLOSE_NEGOTIATION`) — не свободный текст, чтобы не разошёлся со словарём, зашитым на сервере/клиенте Обучения.
- Соединение узлов — переход по выбранному действию к следующему узлу.
- Отметка узлов завершения (`end_states`) — с полями `outcome`.

**Данные и действие:** правки пишутся в `nodes` (и `completion_conditions` для узлов завершения) при сохранении, тот же `PUT /api/scenarios/{id}`.

**Переход:** → экран 5.

---

## 5. Компетенции и индикаторы

**Назначение.** Привязка Scenario к измеряемым компетенциям — отдельно от самого графа, чтобы методист видел покрытие целиком, а не по одному узлу за раз.

**Содержимое:**
- Список проверяемых компетенций (`competencies`) — выбор из 6 кластеров (справочник `competency_clusters`/`indicators` с сервера).
- Правила наблюдения (`observation_rules`) — таблица: семантическое действие → индикатор → условие срабатывания. Для MVP можно редактировать как список, не как визуальный конструктор условий.
- **Отчёт покрытия** — сколько раз каждый выбранный индикатор фактически проверяется в графе (подсчитывается сервером при вызове экрана 6, не здесь — этот экран только задаёт правила, отчёт см. далее).

**Данные и действие:** правки `observation_rules`/`competencies` через `PUT /api/scenarios/{id}`.

**Переход:** → экран 6.

---

## 6. Проверка

**Назначение.** Единая точка обязательной серверной валидации перед публикацией (документ 4, раздел 15 «AI-проверка сценария»).

**Содержимое:**
- Кнопка «Проверить тренировку».
- Результат тремя блоками — ровно по ответу `POST /scenarios/{id}/validate` (server_app_tz.md, раздел 3.1):
  - **Структура**: цель / конфликт / роли / условия завершения — да/нет по каждому.
  - **Логика графа**: список тупиков, недостижимых узлов, циклов (если есть — с указанием конкретного `node_id`, кликабельно — ведёт обратно на экран 4 к этому узлу).
  - **Покрытие индикаторов**: список индикаторов с пометкой «недостаточно контекстов» (`contexts_found < 3`) — прямая отсылка к правилу из architecture_v3.md.
- Если `valid: false` — кнопка «Опубликовать» на экране 8 должна быть недоступна (клиентская подстраховка поверх серверного запрета из server_app_tz.md, `422` при попытке публикации без прохождения проверки).

**Данные:** `POST /api/scenarios/{id}/validate`.

**Переход:** при `valid: true` → экран 7. При `valid: false` → обратно на экран 4/5 по месту найденной проблемы.

## 7. Предпросмотр

**Назначение.** Методист проходит собственный сценарий как обучающийся — «видит то же, что увидит обучающийся» (документ 4, раздел 16).

**Содержимое:**
- Переключатель канала: `[ Chat ] [ Voice ]` (Meeting не показывается — не в MVP).
- Сама тренировка — переиспользует компоненты экранов 3/4 из frontend_training_tz.md (тот же UI, что увидит обучающийся), но в режиме предпросмотра.
- **Event Inspector** — панель сбоку/снизу, показывающая по каждому ходу: действие, состояние, изменение параметров, какой индикатор сработал (документ 4, раздел 16, пример: «Ход #8 → MAKE_CONCESSION → price: −5% → Наблюдение: Concession without reciprocity → Компетенция: Торг и обмен»). Это единственный экран во всём продукте, где индикаторы показываются в реальном времени, — оправдано, потому что аудитория экрана методист, не обучающийся, и принцип «не показывать компетенции во время переговоров» (документ 5) относится к роли обучающегося, не автора.

**Данные:** предпросмотр использует тот же `POST /api/sessions` / `POST /api/sessions/{id}/events`, что и обычное прохождение, с полем `preview: true` (доступно только роли `methodist`) — такие сессии не участвуют в Scoring/Recommendation/профиле (server_app_tz.md, разделы 3.2 и 5; backend_tz.md, раздел 3.3, колонка `is_preview`). Событие всё равно пишется в `events` — иначе не будет данных для Event Inspector.

**Переход:** → экран 8.

---

## 8. Публикация

**Назначение.** Финальный шаг, необратимо (в рамках версии) публикует сценарий.

**Содержимое:**
- Сводка перед публикацией: название, версия (текущая → следующая, например v1.0 → v1.1), список каналов и компетенций.
- Предупреждение, если сценарий уже был опубликован ранее: «Изменения затронут только новые тренировки — уже пройденные сессии не изменятся» (architecture_v3.md, правило версионирования).
- Кнопка «Опубликовать» — недоступна, если экран 6 не пройден с результатом `valid: true` (см. экран 6).

**Данные и действие:** `POST /api/scenarios/{id}/publish`.

**Переход:** → экран 1 (Библиотека), сценарий теперь со статусом «Опубликовано».

---

## 9. История версий

**Назначение.** Просмотр прежних опубликованных версий сценария — не для редактирования, только для сверки.

**Содержимое:**
- Список версий (v1.0, v1.1, v2.0…) с датой публикации.
- Клик по версии — просмотр снимка (`scenario_versions.snapshot`) в режиме только чтения.

**Данные:** нужен эндпоинт `GET /api/scenarios/{id}/versions` — **отсутствует в server_app_tz.md**, требует добавления по тому же принципу, что и `GET /api/users/{id}/sessions` в прошлый раз (простая проекция по `scenario_versions`, сортировка по `published_at DESC`).

## Сквозные требования

- Доступ к любому экрану Конструктора — только роль `methodist` (server_app_tz.md, раздел 1); попытка обращения к `/api/scenarios*` на запись от роли `learner`/`curator` → `403` с сервера, клиент не должен даже показывать эти экраны другим ролям в UI.
- Словарь семантических действий (экран 4) — общий источник правды с клиентом Обучения (frontend_training_tz.md) и с сервером; хранить как разделяемую константу на уровне фронтенд-монорепозитория/пакета, не дублировать вручную в двух местах.
- Автосохранение черновика (экраны 3–5) рекомендуется, так как переходы между экранами графа/компетенций частые — терять правки при случайном уходе с экрана хуже, чем лишний PUT-запрос.
