# ТЗ — фронтенд, модуль «Обучение»

> Клиент для роли «Обучающийся». Работает поверх API из server_app_tz.md. Модуль «Конструктор» (Author Console) и куратор-дашборд — отдельные ТЗ, здесь не описаны. Каналы: Chat и Voice (implementation_roadmap.md, Фаза 1). Все формулировки экранов — по таблице терминов architecture_v3.md: никаких «тест», «правильный ответ», «балл».

---

## 0. Принцип, который держит все экраны вместе

Три визуальных состояния приложения, порядок нарушать нельзя:

```
РАБОЧИЙ ИНСТРУМЕНТ (до)  →  ПЕРЕГОВОРЫ (во время, интерфейс почти невидим)  →  ТРЕНЕР (после)
```

Во время самих переговоров (экраны 3–4) не показываются баллы, индикаторы, названия компетенций — только реплики и доступные действия. Вся аналитика — исключительно после завершения (экраны 5–7).

Фронтенд — тонкий клиент: состояние сессии авторитетно на сервере (`GET /sessions/{id}/state`, ответ `POST /sessions/{id}/events`), фронтенд не хранит и не пересчитывает граф сценария самостоятельно.

---

## Карта экранов

```
1. Главный экран
   ├── 2. Экран выбора/старта тренировки
   │        │
   │        ├── (если mode=arena) → 2а. Подготовка
   │        │
   │        ▼
   │   3. Переговоры — Chat  |  4. Переговоры — Voice
   │        │
   │        ▼
   │   5. Что произошло (Результат)
   │        │
   │        ▼
   │   6. Разбор (Процесс)
   │        │
   │        ▼
   │   7. Профиль (Компетенция)
   │
   └── 8. История тренировок
```

## 1. Главный экран

**Назначение.** Точка входа, задаёт тон всему приложению — это не «пройти тест», а рабочий инструмент переговорщика.

**Содержимое:**
- Три пункта выбора действия: «Подготовиться к переговорам», «Потренироваться в сложной ситуации», «Разобрать прошлые переговоры».
- Если текущая рекомендация имеет источник `curator_assignment` (server_app_tz.md, раздел 3.4) — рядом с пунктом «Потренироваться» короткая пометка «назначено куратором»; если источник `recommendation_engine` — пометки нет, это обычная системная рекомендация.
- Блок «Мой прогресс» — последняя тренировка, одна строка (без цифр/баллов — например «Торг и обмен» как название последней темы).

**Данные с сервера:** `GET /api/users/{id}/recommendation` (для пункта «Потренироваться» и поля `source`), последняя запись из истории сессий (для блока прогресса).

**Переходы:** «Подготовиться»/«Потренироваться» → экран 2. «Разобрать прошлые переговоры» → экран 8.

---

## 2. Экран выбора/старта тренировки

**Назначение.** Показать, какая тренировка предложена и почему, дать выбрать канал, начать сессию.

**Содержимое:**
- Название и краткий контекст сценария (`context.description` из Scenario).
- Причина рекомендации простыми словами (не «индикатор X на уровне 1», а «в прошлый раз вы уступали без запроса встречной ценности»).
- Выбор канала: Chat / Voice.
- Кнопка «Начать переговоры».

**Данные с сервера:** содержимое `Scenario` (без `nodes`/`observation_rules` — это служебные поля, фронтенду не нужны), `recommendation_log.reason` для формулировки причины.

**Переходы:** Если сессия `mode=training` → сразу экран 3/4. Если `mode=arena` → экран 2а.

**Действие:** `POST /api/sessions` при нажатии «Начать переговоры».

---

## 2а. Подготовка (только перед Ареной)

**Назначение.** Рабочий лист переговорщика — переносимые принципы, не сценарные подсказки. Показывается **только** когда стартует тренировка типа «Арена»; для обычной направляемой тренировки этот экран пропускается — интерфейс самой тренировки (видимые варианты действий) уже даёт нужную структуру.

**Содержимое:**
- Поле «Цель».
- Поле «Минимально приемлемый результат».
- Список «Мои приоритеты» (свободный ввод, 2–3 пункта).
- Список «Возможные обмены».
- Кнопка «Начать переговоры».

**Данные:** сохраняются на сервер как есть, без валидации содержания (это самостоятельная работа пользователя, не проверяемое поле).

**Действие:** `POST /api/sessions/{id}/preparation`, затем переход на экран 3/4.

---

## 3. Переговоры — канал Chat

**Назначение.** Само упражнение. Система «почти невидима» — интерфейс похож на рабочий мессенджер, не на форму с вопросами.

**Содержимое:**
- Лента реплик партнёра (сверху) — визуально как чат.
- Область действия обучающегося: либо готовые варианты формулировок (`available_actions[].label`) в виде кнопок/чипов, либо поле свободного ввода, если сценарий это допускает.
- Никаких индикаторов, счётчиков, прогресс-баров компетенций на этом экране.

**Данные с сервера:** `current_node` из ответа `POST /sessions` или `POST /sessions/{id}/events` — `text` партнёра и `available_actions`.

**Действие при выборе действия:** `POST /api/sessions/{id}/events` с выбранным `action_id` → получить новый `next_node` → отрисовать. Если `next_node: null` → вызвать `POST /sessions/{id}/complete` → переход на экран 5.

**Технически:** генерировать и отправлять `client_event_id` (UUID) на каждое действие — для идемпотентности (server_app_tz.md, раздел 5).

---

## 4. Переговоры — канал Voice

**Назначение.** То же упражнение, голосовой интерфейс. Использует ту же сессию/состояние, что и Chat — отличается только чрома экрана.

**Содержимое:**
- Экран в стиле «идёт звонок»: имя/роль партнёра, таймер разговора, индикатор «звонок идёт».
- Озвучка реплики партнёра — браузерный `SpeechSynthesis`.
- Распознавание речи обучающегося — браузерный `SpeechRecognition` (Web Speech API); распознанный текст сопоставляется с ближайшим `available_actions[].label` **на клиенте перед отправкой** — сервер по-прежнему принимает только `action_id` из текущего набора, не свободный текст (не нарушает принцип «никакого NLP в рантайме на сервере» — сопоставление здесь тривиальное, near-exact-match на клиенте, не LLM).
- Кнопки «Пауза» / «Завершить».
- **Важно (см. free_tier_plan.md, риск лёгких моделей):** если распознанная фраза не сопоставляется уверенно ни с одним доступным действием — показать пользователю короткий список вариантов для ручного выбора, не гадать и не отправлять на сервер невалидный `action_id`.

**Данные и действие:** идентичны экрану 3 (`POST /api/sessions/{id}/events` с тем же `action_id`).

**Ограничение среды:** Web Speech API наиболее стабильно работает в Chrome — на демо использовать именно этот браузер (implementation_roadmap.md, День 3, чек-лист репетиции).

## 5. Что произошло (Результат)

**Назначение.** Первый экран после завершения — факты по условиям сделки, не оценка.

**Содержимое:**
- Список изменений параметров: `outcome` (например «Контракт продлён на 12 месяцев», «Цена снижена на 10%»).
- Отметки по целям: достигнута/не достигнута — без процентов и баллов.
- Кнопка «Разобрать переговоры».

**Данные с сервера:** `analysis.result` из `GET /api/sessions/{id}/analysis`.

**Переход:** → экран 6.

---

## 6. Разбор (Процесс)

**Назначение.** Хронология ключевых ходов как история, не список ошибок.

**Содержимое:**
- Последовательность шагов: краткое summary каждого значимого хода («Вы запросили условия» → «Клиент назвал ограничения» → «Вы предложили скидку 10%»).
- Один выделенный «ключевой момент» — не более одного на экран, чтобы не перегружать разбор.

**Данные с сервера:** `analysis.process` и `analysis.key_moment`.

**Переход:** → экран 7.

---

## 7. Профиль (Компетенция)

**Назначение.** Единственное место, где впервые появляется слово «профиль» — наблюдение о поведении в конкретной тренировке, не оценка личности.

**Содержимое:**
- По каждому кластеру, затронутому в этой тренировке: короткое наблюдение в свободной форме («Вы хорошо удерживаете основную цель, но при давлении склонны ускорять уступки»), не «балл 2/4».
- Явно **запрещённые** формулировки на этом экране (architecture_v3.md, раздел 0): «вы жёсткий переговорщик», «ваш тип» и т.п.
- Кнопка «Следующая тренировка» — ведёт на экран 2 с новой рекомендацией.

**Данные с сервера:** `analysis.competency`, дополнительно можно подтянуть `GET /api/users/{id}/recommendation` для кнопки-перехода.

---

## 8. История тренировок

**Назначение.** Точка входа «Разобрать прошлые переговоры» с главного экрана — список прошлых сессий для повторного просмотра разбора.

**Содержимое:**
- Список завершённых сессий: дата, название сценария, канал.
- Клик по элементу → повторно открывает экраны 5–6–7 для этой сессии (те же данные, `GET /api/sessions/{id}/analysis`, но без возможности что-то изменить — просмотр архива).

**Данные с сервера:** список сессий пользователя (эндпоинт `GET /api/users/{id}/sessions` — не описан в server_app_tz.md явно, нужно добавить как простую проекцию по `sessions` таблице, фильтр `status='completed'`, сортировка по `completed_at`).

## Сквозные технические требования фронтенда

- Состояние сессии не кэшируется и не восстанавливается локально между перезагрузками страницы дальше текущего узла — при обрыве соединения повторный `GET /sessions/{id}/state` восстанавливает актуальную точку с сервера.
- Никакого `localStorage`/`sessionStorage` для данных сессии — только серверное состояние плюс временные React-переменные на время рендера текущего экрана.
- Единый компонент для отображения `available_actions` переиспользуется между экранами 3 и 4 (Chat/Voice) — различается только обвязка ввода (текстовое поле/кнопки vs микрофон), логика отправки действия — одна.
