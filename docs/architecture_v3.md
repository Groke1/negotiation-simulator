# «Арена переговоров» — методика и архитектура (v3)

> Заменяет architecture_v2.md. Не отменяет прежние решения (свой JSON-формат, семантический слой действий, 4 источника данных, офлайн-принцип, роли, стек), а достраивает их до полного цикла: Подготовка → Арена → Наблюдение → Разбор → Профиль → Развитие → Новая Арена.

---

## 0. Что изменилось относительно v2 — кратко

| Было (v2) | Стало (v3) |
|---|---|
| Один объект «Scenario» = граф диалога | Два объекта: **Scenario** (описание переговорного мира) и **Session** (история конкретных переговоров внутри него) |
| Профиль строится сразу после прохождения | Явный 7-шаговый цикл, с обязательной **Подготовкой** перед каждой Ареной |
| Один режим (виртуальный партнёр) + 4 источника данных как варианты сбора | Два официальных режима — **Тренировочная Арена** и **Живая Арена** — и 4 источника переупакованы как способы получения данных внутри этих режимов |
| Разбор = «что произошло / разбор / профиль» (3 экрана) | Разбор = **Результат / Процесс / Наблюдение / Компетенция** — 4 разделяемых слоя, «Наблюдение» присутствует только в Живой Арене |
| ИИ не в рантайме ученика (неявный принцип) | Явный принцип: **ИИ не становится судьёй** — ни в Тренировочной, ни тем более в Живой Арене; эксперт не заменяется |
| Адаптивность — то ли навык, то ли нет (противоречие между исследованием и черновиком) | Разрешено: адаптивность — **поперечная характеристика**, измеряется через устойчивость остальных 6 компетенций при росте сложности, не отдельный балл (обоснование — раздел 5) |

## 1. Терминология

Добавляется к таблице терминов из v2 (тестовый язык → язык продукта — без изменений):

> **Важное исправление после обсуждения.** В первой версии этого документа Арена была ошибочно поднята на уровень всей системы («Тренировочная Арена» = любая тренировка вообще). Это неверно. Ниже — исправленные определения.

| Термин | Определение |
|---|---|
| **Практика** | Основной, самый частый вид активности в приложении (условно 90% времени) — направляемая тренировка с виртуальным партнёром, где обучающемуся видны доступные варианты действий, а сама структура интерфейса уже задаёт часть подсказок |
| **Арена** | Один из типов упражнения внутри Практики, не отдельная система и не основной режим — свободная ситуация без подсказанных вариантов действий, более высокая ставка, используется редко: как проверка переноса навыка, а не как повседневное упражнение |
| **Живая Арена** | Ещё более редкий, продвинутый частный случай Арены — переговоры двух реальных людей, каждый со своей закрытой информацией, под наблюдением эксперта |
| **Scenario** | Описание переговорного мира: контекст, роли, цели, интересы, ограничения, параметры, скрытая информация, сложность, компетенции, правила наблюдения, условия завершения. Используется и для обычной Практики, и для Арены — формат один |
| **Session** | Конкретная история переговоров внутри Scenario: кто участвовал, что произошло, какие события зафиксированы, чем закончилось |
| **Подготовка** | Короткий рабочий лист (цель, границы, интересы) непосредственно перед конкретной Ареной — не перед каждой обычной Практикой и не «вход в приложение» вообще. В обычной Практике эту роль уже выполняет сам интерфейс (видимые варианты действий), поэтому отдельный шаг не нужен |

Главный принцип раздела: **Scenario — это ситуация. Session — это реальная история переговоров внутри этой ситуации.** Один Scenario порождает множество разных Session — это и отличает Арену от прежнего «диалогового дерева», где сценарий и есть единственно возможный разговор.

## 2. Роли

Обновляется относительно v2 — «Куратор» и «эксперт/судья» объединены, так как в методике это одна и та же функция наблюдения и развития, просто в разных режимах Арены:

| Роль | Что делает |
|---|---|
| **Обучающийся** | Проходит Подготовку → выходит на Арену → получает Разбор → развивает Профиль |
| **Разработчик курсов / методист** | Создаёт Scenario через AI Scenario Builder, редактирует, публикует, задаёт правила наблюдения и условия завершения |
| **Куратор / эксперт** | В Тренировочной Арене — видит профили и протоколы, назначает тренировки. В Живой Арене — дополнительно выступает **судьёй**: наблюдает за процессом вживую, фиксирует значимые проявления поведения |

## 3. Учебный цикл — два уровня

**Внешний цикл — основной, не менялся с самой первой версии продукта.** Это то, ради чего человек вообще открывает приложение — подготовка к реальным переговорам вне системы, а не к Арене:

```
Диагностика → Профиль → Рекомендация → Практика → (обновлённая) Диагностика → ...
```

1. **Диагностика** — первичная оценка через тренировочный сценарий.
2. **Профиль** — карта компетенций по итогам.
3. **Рекомендация** — что практиковать дальше; в подавляющем большинстве случаев — обычная направляемая тренировка, иногда (см. ниже) — Арена.
4. **Практика** — основной объём времени пользователя в системе.

**Внутренний цикл — включается только когда конкретное упражнение внутри Практики оказывается Ареной**, не при каждой сессии:

```
Подготовка → Арена → Наблюдение → Разбор → Профиль
```

Здесь «Профиль» — тот же самый профиль компетенций, что и во внешнем цикле, просто обновляемый данными именно этой Арена-сессии; отдельного параллельного профиля не существует. Обычная тренировка тоже обновляет профиль — просто без шага «Подготовка» и без слоя «Наблюдение» (раздел 8), так как в ней нет второго человека и явный рабочий лист не нужен — интерфейс уже даёт нужную структуру через видимые варианты действий.

## 4. Три уровня практики — от основного к редкому

| | Обычная тренировка | Арена | Живая Арена |
|---|---|---|---|
| Доля времени пользователя | ~90% | Редко, точечно | Ещё реже |
| Участники | Обучающийся + виртуальный партнёр | Обучающийся + виртуальный партнёр | Два реальных человека |
| Подсказки в интерфейсе | Видимые варианты действий на каждом шаге | Нет — свободная ситуация | Нет — свободная ситуация |
| Нужна Подготовка (рабочий лист)? | Нет — интерфейс сам даёт структуру | Да | Да |
| Источник данных | Автоматическая разметка по графу | Автоматическая разметка по графу (более гибкий/свободный ввод) | Триангуляция: Intention + Perception + Judge (раздел 7) |
| Устройство | Телефон офлайн + ПК | ПК преимущественно | ПК/очно, требует эксперта |
| Роль ИИ | Не участвует в рантайме | Не участвует в рантайме | Не участвует вообще — не заменяет эксперта (раздел 9) |
| Статус в MVP хакатона | **Основной объём** | Опционально, если останется время | Концепт в презентации, не код |

Все три уровня описываются одним и тем же форматом Scenario — уровень не меняет мир, меняет только то, насколько свободен ввод обучающегося и появляется ли перед сессией отдельный шаг Подготовки.

## 5. Компетенции — разрешение противоречия между документами

6 кластеров компетенций (без изменений от architecture_v2.md, источник — Smolinski & Xiong 2020 и матрица индикаторов): цели и границы; диагностика; создание ценности; аргументация; торг и обмен; конфликт и регуляция.

**Адаптивность не седьмой кластер**, несмотря на то что в одном из черновиков (документ про Арену) она перечислена в общем списке для читаемости. Операционально (раздел 11 того же документа: «диагностика проявляется в спокойной ситуации, но снижается под давлением») адаптивность — это именно то, что architecture_v2.md уже определял как поперечную характеристику: устойчивость каждой из 6 компетенций при росте сложности сценария, а не отдельный седьмой балл. Индикаторы адаптивности из черновика («меняет стратегию», «возвращается к диагностике», «меняет предмет переговоров») используются как раз для того, чтобы **вычислить** эту устойчивость — не как отдельная компетенция, а как метод измерения остальных шести под нагрузкой.

## 6. Scenario и Session — свой JSON-формат (обновлённая схема)

### Scenario — описание мира

```json
{
  "scenario_id": "uuid",
  "version": "2.0",
  "title": "Продление контракта — ценовой конфликт",
  "mode_support": ["training", "live"],
  "context": {
    "situation_type": "продление контракта",
    "conflict_type": ["цена", "срок"],
    "description": "Клиент хочет продлить контракт, но требует скидку 15%."
  },
  "roles": [
    { "id": "learner", "label": "Менеджер по продажам" },
    { "id": "partner", "label": "Клиент" }
  ],
  "goals": {
    "learner": "Сохранить контракт на 12 месяцев",
    "partner": "Снизить цену минимум на 15%"
  },
  "interests": {
    "learner": ["долгосрочный контракт", "сохранить маржу"],
    "partner": ["снизить издержки", "гарантии качества"]
  },
  "constraints": {
    "learner": { "max_discount": 0.07 },
    "partner": { "min_discount": 0.15, "alternative_supplier": true }
  },
  "parameters": [
    { "key": "price", "initial": 100, "unit": "%" },
    { "key": "contract_term_months", "initial": 12 },
    { "key": "sla_level", "initial": "standard" }
  ],
  "private_information": {
    "learner": { "can_offer": ["extended_sla", "longer_term"] },
    "partner": { "has_alternative_supplier": true, "reveals_if": "asked_directly" }
  },
  "difficulty": "L2",
  "competencies": ["Цели и границы", "Торг и обмен", "Диагностика"],
  "observation_rules": [
    {
      "semantic_action": "REQUEST_RECIPROCITY",
      "cluster": "Торг и обмен",
      "indicator": "Запрашивает встречную ценность",
      "trigger_condition": "после получения уступки от партнёра"
    }
  ],
  "completion_conditions": [
    { "type": "agreement", "condition": "price_change >= -0.07 AND contract_term_months >= 6" },
    { "type": "no_deal", "condition": "learner_action == CLOSE_NEGOTIATION" }
  ],
  "channels": ["chat", "voice", "meeting"],
  "nodes": [ /* граф для Тренировочной Арены — формат без изменений от architecture_v2.md */ ]
}
```

Новое относительно v2: `mode_support`, `private_information`, `observation_rules` (заменяют разрозненные теги индикаторов на реплике единым правилом, применимым что к узлу графа, что к живому наблюдению), `completion_conditions` как отдельный явный блок.

### Session — история конкретных переговоров

```json
{
  "session_id": "uuid",
  "scenario_id": "uuid",
  "scenario_version": "2.0",
  "mode": "live",
  "channel": "meeting",
  "participants": [
    { "role": "learner", "actor_type": "human", "actor_id": "user_123" },
    { "role": "partner", "actor_type": "human", "actor_id": "user_456" }
  ],
  "judge_id": "expert_789",
  "events": [ /* Event Log — формат xAPI-подобный, без изменений от architecture_v2.md, verb = семантическое действие */ ],
  "intentions": [
    { "event_id": "e5", "actor": "learner", "stated_intention": "Хотел открыть пространство для обмена" }
  ],
  "perceptions": [
    { "event_id": "e5", "actor": "partner", "perceived_as": "Понял, что он готов снижать цену" }
  ],
  "judge_observations": [
    { "event_id": "e5", "observation": "Граница была сформулирована неоднозначно", "indicator_tags": [ { "cluster": "Цели и границы", "indicator": "Удерживает ключевое условие", "flag": "неоднозначно" } ] }
  ],
  "outcome": { "contract_extended": true, "price_change": -0.10, "sla_change": "extended" },
  "analysis": { "result": {}, "process": {}, "observation": {}, "competency_profile": {} }
}
```

Для **Тренировочной Арены** та же структура Session используется, но `participants` состоит из `learner` + `virtual_partner`, а блоки `intentions`/`perceptions`/`judge_observations` — пустые: индикаторы вычисляются автоматически из `events` по `observation_rules` сценария, без участия человека. Один формат Session обслуживает оба режима — не два разных типа записи.

## 7. Триангуляция для Живой Арены

Три независимых источника на одно и то же событие переговоров:

| Источник | Вопрос | Пример |
|---|---|---|
| **Intention** (намерение) | Что переговорщик хотел сделать этой репликой? | «Я хотел открыть пространство для обмена» |
| **Perception** (восприятие) | Что понял из этой реплики партнёр? | «Я понял, что он готов снижать цену» |
| **Judge** (наблюдение эксперта) | Что увидел независимый наблюдатель? | «Граница была сформулирована неоднозначно» |

**Расхождение между намерением и восприятием — не ошибка, а материал для разбора.** Это прямое продолжение принципа v2 «мы описываем поведение, а не человека»: несовпадение трёх точек зрения точнее показывает переговорный эффект действия, чем любая из них по отдельности.

Практическое следствие для интерфейса: в Живой Арене после каждого значимого хода (или в конце сессии, если фиксация в реальном времени мешает потоку) обучающийся и партнёр коротко отмечают намерение/восприятие, а эксперт — параллельно и независимо — ведёт судейский лист. Три записи не показываются друг другу до завершения — иначе теряется независимость источников.

## 8. Четырёхслойный разбор (заменяет три экрана из v2)

| Слой | Вопрос | Есть в Тренировочной Арене | Есть в Живой Арене |
|---|---|---|---|
| **Результат** | Что произошло с условиями сделки? | Да | Да |
| **Процесс** | Какие действия совершал обучающийся? | Да | Да |
| **Наблюдение** | Что увидели партнёр и эксперт? | Нет (нет второго человека) | Да — из триангуляции |
| **Компетенция** | Какой поведенческий паттерн проявился? | Да | Да |

Явный принцип раздела (без изменений от прежней логики, но теперь закреплён как отдельный слой, а не смешан с результатом): **результат сделки не равен компетенции.** Переговорщик может получить выгодную сделку благодаря сильной позиции и при этом показать слабый процесс; и наоборот. Оба факта должны быть видны раздельно, не свёрнуты в один балл.

Три экрана Тренировочной Арены из v2 («Что произошло → Разбор → Профиль») остаются верными как последовательность интерфейса, но теперь соответствуют слоям Результат → Процесс → Компетенция; слой Наблюдение добавляется отдельным экраном только в Живой Арене.

## 9. Принцип: ИИ не становится судьёй

Расширяет принцип v2 «ИИ только у автора, не в рантайме ученика» на явный запрет для Живой Арены:

- ИИ (AI Scenario Builder) создаёт черновик Scenario — не более.
- ИИ никогда не генерирует `judge_observations`, не оценивает `intentions`/`perceptions`, не выставляет компетенции в Живой Арене.
- В Тренировочной Арене оценка остаётся детерминированной (rules-based по `observation_rules`), не LLM-классификатором — тот же принцип, что и в v2, здесь не меняется.
- Платформа **оцифровывает работу эксперта** (структурирует судейский лист, сравнивает оценки, строит профиль из них), но не заменяет его решение.

Это не только этический принцип, но и прямое следствие раздела 6 исследования измеримости (architecture_v2.md, источник) — «осознанность выбора» и «скрытые мотивы» прямо помечены как то, что не стоит обещать автоматизировать.

## 10. Источники данных — перепривязка к режимам Арены

Прежняя модель 4 источников (v2, раздел 7) не отменяется, а становится конкретизацией двух режимов:

| Источник (из v2) | Режим Арены | Как теперь называется |
|---|---|---|
| 1. Виртуальный партнёр, граф | Тренировочная Арена | Основной источник Session в Тренировочной Арене |
| 2. Наблюдатель вживую | Живая Арена | Judge (часть триангуляции) |
| 3. Взаимооценка после разговора | Живая Арена | Perception, собранная постфактум, если фиксация в реальном времени невозможна |
| 4. Запись + локальная транскрипция | Живая Арена (опционально) | Вспомогательный инструмент для Judge — расшифровка для последующего разбора, не источник автоматической оценки |

Веса источников в профиле — правило из v2 сохраняется: калибровочная сессия с высоким весом, накопительные данные — с понижающим, обязательное подтверждение перед официальным повышением уровня.

## 11. Подготовка — отдельный модуль

Обязательный этап перед каждой Ареной. Формирует переносимые принципы, не привязку к конкретному сценарию:

**Не учим**: «если собеседник сказал X, отвечай Y».
**Учим**: «если не хватает информации — исследуй интересы»; «если делаешь уступку — ищи встречную ценность»; «если возникает давление — удерживай цель и адаптируй тактику».

Интерфейсно — рабочий лист переговорщика (уже был намечен в предыдущей проработке UX для канала Meeting, теперь становится универсальным шагом перед любой Ареной, не только очной): цель, минимально приемлемый результат, приоритеты, предполагаемые интересы партнёра, возможные обмены.

Содержание Подготовки для конкретного обучающегося берётся из раздела «Развитие» предыдущего цикла (шаг 6 учебного цикла) — если прошлый Профиль показал дефицит в «Торг и обмен», следующая Подготовка целенаправленно тренирует именно поиск встречной ценности, а не даёт общий чек-лист.

## 12. Что это меняет в объёме MVP

Коротко — подробности в обновлённом `submission_interim.md`:

- **Основной объём хакатона — обычная тренировка** (направляемый граф, видимые варианты действий), не Арена. Именно она отрабатывает полный внешний цикл: Диагностика → Профиль → Рекомендация → Практика.
- **Каналы: Chat + лёгкий рабочий Voice (STT/TTS)** — решение подтверждено; Chat остаётся основным, Voice реализуется как второй рабочий канал вместо прежнего плана «Meeting как концепт-скриншот». Meeting-канал (очная встреча) переносится в раздел «не входит в MVP» полностью — не был приоритетом ни в одной версии плана.
- Экран Подготовки нужен только если в MVP успевает войти Арена как опциональное упражнение — для обычных тренировок он не строится, интерфейс уже даёт нужную структуру через видимые действия.
- Разбор — 3 экрана (Результат/Процесс/Компетенция) для обычной тренировки; слой «Наблюдение» не показывается — он появляется только в Живой Арене, которая в MVP не реализуется как код.
- Живая Арена (триангуляция, судейский лист) — концепт для презентации, не рабочий код.

## 13. Открытые вопросы

1. Как фиксировать Intention/Perception в реальном времени, не разрушая поток живых переговоров (пауза после каждого хода vs один общий срез в конце) — решение методическое, не техническое, требует пилота с реальными парами.
2. Нужно ли поддерживать в Scenario оба режима ветвления одновременно (классическое дерево узлов + состояние-ориентированная модель с условиями изменения ситуации) или выбрать один — черновик допускает оба, но для MVP выбран только графовый (проще реализовать детерминированно).
3. Калибровка шкалы 0–4 (architecture_v2.md, раздел 9) теперь должна проводиться раздельно для Тренировочной и Живой Арены — данные из них по надёжности не эквивалентны (см. раздел 10), это может потребовать двух отдельных калибровочных выборок, а не одной общей.
