# План-график реализации — «Арена переговоров» (внутреннее название модуля: Конструктор переговорных тренировок)

> Допущение: старт 15 сентября 2026, команда из 3 разработчиков. Если это неверно — тайминг ниже нужно пересчитать, но структура фаз и зависимости между ними останутся теми же.
>
> **Обновлено под официальное ТЗ хакатона (Алабуга, 2026), затем — под уточнение методики.** Три изменения относительно прежней версии: 1) для хакатонной части платформа — веб-стек вместо нативного Flutter/Android, поскольку ТЗ требует демо без установки и нестандартного железа на устройстве жюри; нативное Android/Flutter-приложение остаётся планом на постхакатонный этап (Фаза 2+). 2) Добавлен обязательный чекпоинт промежуточной сдачи внутри Фазы 1. 3) **Основной объём MVP — обычный цикл Диагностика → Профиль → Рекомендация → Практика (направляемая тренировка), не Арена** — Арена вошла в план как опциональный элемент, если останется время; вместо второго канала-концепта (Meeting) в MVP включён рабочий голосовой канал (Voice, STT/TTS). Во всех материалах для жюри используется официальное имя задачи — «Арена переговоров»; внутренние названия модулей (Конструктор переговорных тренировок, AI Scenario Builder) — технические термины внутри документации. Актуальная методика — `architecture_v3.md`, а не v2.

## 0. Разделение ролей на команду из 3

| Роль | Отвечает за | Основные компоненты из architecture_v2.md |
|---|---|---|
| **Dev A — Web-клиент обучающегося** | Движок диалога, интерфейс прохождения тренировки, адаптивная вёрстка под мобильный экран браузера | Scenario Engine (JS/TS-порт), Event Log (клиент), локальное хранение состояния сессии |
| **Dev B — Backend** | API, база данных, профиль, рекомендации | PostgreSQL, Event Log (сервер), Profile Engine, Recommendation Engine (rules-based) |
| **Dev C — Web/AI** | Конструктор, ИИ-интеграция | React Author Console, React Flow, AIProvider (Mock → Cloud), валидация Scenario-JSON |

**Про Flutter.** Нативное Android-приложение с офлайн-движком (Scenario Engine на Dart, SQLite/Drift, WorkManager-синхронизация) — правильная цель для полного продукта, но не для хакатонного MVP: ТЗ требует, чтобы жюри могло запустить прототип «без нестандартного железа и долгой ручной настройки», а веб-ссылка в браузере — самый низкий барьер для этого. Перенос движка диалога с Dart на веб-стек не будет потерян: единый JSON-формат сценария (architecture_v2.md, раздел 3) и словарь семантических действий одинаковы для обеих реализаций, поэтому логика, отработанная на вебе для хакатона, напрямую переносится в Dart-версию на Фазе 2+.

Параллелизация возможна с первого дня: пока Dev A и Dev B строят детерминированное ядро на едином формате данных (JSON-схема сценария + Event Log), Dev C строит конструктор поверх `MockAIProvider`, не дожидаясь готовности остальных частей — они встретятся на общем JSON-формате, зафиксированном заранее.

## Фаза 1 — Хакатон-спринт (15–17 сентября, 3 дня)

Цель фазы: рабочее демо основного цикла (направляемая тренировка, не Арена) в двух каналах — Chat и Voice — с полным циклом от прохождения тренировки до разбора и профиля, доступное жюри по публичной веб-ссылке.

### День 1 (15 сентября)

| Роль | Задачи |
|---|---|
| Dev A | Разбор JSON-схемы в TS-модели; интерпретатор графа сценария (узел → действие → переход) на тестовом сценарии; каркас веб-клиента (React или аналог) под оба канала |
| Dev B | Схема PostgreSQL под профиль *(индикатор, уровень, источник, вес)* и Event Log; минимальный REST-эндпоинт приёма событий |
| Dev C | React Author Console: экран «Библиотека тренировок» + экран «Описать тренировку своими словами»; `MockAIProvider`, возвращающий заранее подготовленный Scenario-JSON |
| Все | → к концу дня: промежуточная сдача (см. блок выше) |

### День 2 (16 сентября)

| Роль | Задачи |
|---|---|
| Dev A | UI прохождения тренировки в канале Chat (документ про интерфейс: «рабочий инструмент → переговоры → тренер»); запись событий в Event Log при каждом выборе действия |
| Dev B | Rules-based Scoring: подсчёт индикаторов из накопленных событий по MVP-подмножеству (architecture_v3.md, раздел 5); Profile Engine, отдающий карту по 6 кластерам |
| Dev C | Экран «Переговорное дерево» (визуализация через React Flow) + шаг валидации Scenario-JSON (структура/логика графа) |

### День 3 (17 сентября)

| Роль | Задачи |
|---|---|
| Dev A | Канал Voice поверх готового Chat-движка: браузерный **Web Speech API** (SpeechRecognition на вход, SpeechSynthesis на озвучку реплик партнёра) — бесплатно, без сервера, без внешнего API; тот же граф сценария и Event Log, что и в Chat. Три экрана после тренировки: «Что произошло» → «Разбор» → «Профиль», без языка тестирования |
| Dev B | Recommendation Engine (минимальная rules-based версия: слабый индикатор → следующая тренировка из библиотеки) |
| Dev C | Подключение `CloudAIProvider` для живой генерации на демо (5–20 вызовов); финальная сборка Author Console |
| Все | Репетиция демо на реальном (не Mock) сценарии в обоих каналах; проверка «холодного старта», если демо публичное; проверка Web Speech API в браузере, который будет использован на показе (лучшая поддержка — Chrome) |

**Что сознательно не входит в хакатон-спринт**: Meeting-канал — не входит ни в каком виде; Арена (как опциональный тип упражнения) и Живая Арена — не в основном объёме, Арена добавляется отдельно при наличии времени (см. блок ниже); калибровка шкалы 0–4 — не начата; куратор-дашборд — не строится, если не останется времени.

### Опционально, если останется время после Дня 3

Арена как отдельный, более свободный тип упражнения (без подсказанных вариантов действий, короткий экран Подготовки перед ней) — добавляется поверх уже готового и стабильного основного цикла, не вместо него. Не начинать эту работу, пока основной цикл в обоих каналах не работает целиком и не отрепетирован.

## Фаза 2 — Постхакатонное укрепление MVP (18 сентября – 9 октября, ~3 недели)

Цель: то, что было закреплено на скорую руку под демо, довести до состояния, пригодного для реальных пользователей (не жюри).

| Неделя | Dev A | Dev B | Dev C |
|---|---|---|---|
| 1 (18–24 сент) | Синхронизация телефон↔сервер (WorkManager + append-only лог протоколов) | Полноценный API с аутентификацией; миграции схемы | Полный редактор графа (ручное редактирование черновика, не только просмотр) |
| 2 (25 сент–1 окт) | ПК-версия (Flutter Desktop) для калибровочных сессий | Куратор-дашборд: профили команды, протоколы сессий | Правила контроля качества в конструкторе (покрытие индикатора ≥3 контекстов, автоматическая проверка перед публикацией) |
| 3 (2–9 окт) | Тестирование на слабом устройстве (см. free_tier_plan / прежние заметки про офлайн-CRM); исправление узких мест | Версионирование опубликованных сценариев (v1.0 → v1.1, без изменения результатов уже пройденных тренировок) | Событийный инспектор (Event Inspector) для предпросмотра автором |

По итогам фазы — рабочий MVP с двумя ролями из трёх активно используемыми (обучающийся, разработчик курсов); куратор — база готова, но не отполирована.

## Фаза 3 — Экспертная калибровка шкалы (параллельно с фазой 2, 18 сентября – конец октября)

Это не разработка, а методическая работа, которая может идти параллельно кодированию, но блокирует переход шкалы 0–4 из статуса «гипотеза» в «рабочая метрика» (architecture_v2.md, раздел 9). Не требует всех 3 разработчиков — можно вести силами одного методиста/автора + внешних экспертов.

| Шаг | Срок | Результат |
|---|---|---|
| Собрать 20–30 сценарных микро-ситуаций, покрывающих спорные индикаторы | 2 недели | Черновая библиотека для разметки |
| Разметка минимум двумя независимыми экспертами по единому руководству | 2 недели | Два набора оценок на один и тот же материал |
| Подсчёт согласованности экспертов | несколько дней | Метрика межэкспертного согласия |
| Отбор индикаторов, которые реально различают уровень (не только стиль речи) | несколько дней | Финальное MVP-подмножество индикаторов, подтверждённое, а не гипотетическое |

Результат фазы напрямую влияет на Profile Engine (Dev B) — веса и пороги уровней должны быть обновлены по итогам калибровки, а не оставлены как в хакатонной заглушке.

## Фаза 4 — Пилот (ноябрь и далее)

Начинается только после того, как фазы 2 и 3 закрыты одновременно — досрочный пилот на некалиброванной шкале подрывает доверие к продукту у первого же клиента.

- Подключение первой пилотной группы (реальные обучающиеся + куратор).
- Запуск источников 2–4 (наблюдатель, взаимооценка, запись+транскрипция) — в хакатон-MVP их не было, они строятся отдельно поверх уже стабильного источника 1 (виртуальный партнёр).
- Сбор данных для контрольного сравнения «до/после» через 5–7 тренировок на реальных пользователях.
- Первая метрика для инвестора/куратора: не абстрактный % улучшения, а конкретные протоколы с подтверждённым переходом уровня индикатора.

## Зависимости, которые нельзя нарушать

1. Фаза 1 не может начаться без зафиксированной JSON-схемы (Фаза 0) — иначе Dev A/B/C разойдутся по несовместимым форматам уже в первый день.
2. Фаза 4 не может начаться без завершённой Фазы 3 — калибровка шкалы обязательна перед реальными пользователями, даже если код давно готов.
3. Meeting-канал добавляется только после того, как Chat и Voice прошли Фазу 2 полностью — семантический слой действий один на все каналы, поэтому их стабильность в двух уже реализованных каналах — предпосылка для третьего, а не отдельная работа с нуля.
4. Арена (как опциональный тип упражнения) добавляется только поверх стабильного основного цикла — не может стать заменой ему ни на каком этапе, включая пилот.
